## Context

动机见 [proposal.md](proposal.md)，行为要求见随附的 desktop-window-rules、rule-snapshots 和 configuration-backup 规格。当前应用将清理锁定存储在 `window-cleanup-locks.json`，每个具名桌面布局快照则在 `desktop-layout-snapshots.json` 内嵌一组独立的位置与匹配记录。重新捕获快照会替换这些记录并丢失用户编辑的正则表达式。现有快照匹配器已提供保守身份评分、预览、进度和创建桌面的能力，可复用于全局规则集合。

项目是 .NET Framework 4.7.2 WinForms 托盘应用。它没有测试项目，使用单文件 JSON 原子写入，并要求在实现变更后重启 Debug 应用。设置存储在 `%APPDATA%\WindowsVirtualDesktopHelper`，必须保持设置键的向后兼容。

## Goals / Non-Goals

**Goals:**
- 使手工桌面匹配修改在常规规则更新后仍可保留。
- 让清理规则和桌面位置规则可独立使用，同时允许一份历史快照一起恢复二者。
- 保留保守匹配机制，防止自动同步修改存在歧义的规则。
- 无论界面是否可见，只要应用运行即可执行自动捕获，且不阻塞 WinForms 线程。
- 导入现有本地数据和便携备份时，不丢弃旧格式无法表达的规则。

**Non-Goals:**
- 不捕获或恢复窗口尺寸位置、显示器位置、应用文档、进程状态、浏览器标签页或当前活动桌面。
- 不删除虚拟桌面，也不依据所有权无法解析或显示在所有桌面上的窗口修改规则。
- 不自动应用已恢复或更新的桌面规则；窗口归位必须由用户明确触发。
- 不提供导入规则状态与本地规则状态的交互式合并。

## Decisions

### 在一个版本化文档中保存全部规则状态

以版本化 `desktop-rule-state.json` 文档替代彼此独立且可变的规则文件。该文档包含当前清理锁定规则、当前全局桌面规则和快照历史。共享状态仓库负责验证和原子文件替换；专用的清理、桌面规则和快照服务在此状态上提供各自范围的操作。

此方案避免跨两个文件仅恢复一部分的情况，并让一次捕获的快照成为两套集合的一致版本。保留独立文件并在写入失败时手工补偿被否决，因为完整快照恢复仍会在两次替换之间存在崩溃窗口。

结构中区分 `Manual`、`Automatic` 和 `Legacy` 快照类型。完整快照持有复制后的清理锁定和桌面规则集合。旧快照持有复制后的桌面规则并标记清理规则集合不可用，以便恢复时保留当前清理集合而非伪造历史数据。

### 将现有已保存窗口记录提升为可复用的桌面规则

保留 `SnapshotWindow` 现有的稳定身份字段和标题正则行为，但将每条记录作为全局 `DesktopRule` 而不是具名布局中的条目。目标桌面沿用当前解析策略：优先使用仍存在的已保存桌面身份，否则使用保存的从零开始顺序；仅在用户明确应用规则时创建缺失的桌面后缀。

桌面规则应用复用现有评分匹配算法及预览/结果模型，从而保留“歧义候选绝不移动”的约束。简化为进程名/标题匹配的方案被否决，因为它会削弱对同一应用重复窗口的既有保护。

### 通过双向歧义检查增量同步当前窗口

`更新桌面规则` 一次性收集所有桌面上所有权可解析为普通虚拟桌面的合格窗口。随后在得到完整映射前不修改当前规则。仅当一条规则映射到恰好一个当前窗口，且该窗口也仅映射到这条规则时，才更新规则目标。对于未映射到规则的当前窗口新增精确规则；对映射存在歧义、映射到不同桌面窗口或因窗口关闭而未映射的规则保持不变。操作向界面返回数量和冲突详情。

双向检查可防止宽泛正则表达式因多个打开窗口而被静默重新定向。使用观察到的窗口覆盖匹配元数据被否决，因为这正是用户正则表达式丢失的根源。

### 将全局操作放置在内置管理器右下角操作区

在 `WindowOverviewForm` 现有清理控件旁增加三个固定宽度按钮：`更新桌面规则`、`管理桌面规则` 和 `应用桌面规则`。桌面规则编辑器从当前快照所属的窗口规则窗体改造而来，但读写全局集合，并始终列出全部目标桌面规则。应用操作对所有全局规则使用现有预览/进度窗体。

移除旧的快照专属 `编辑窗口规则` 操作及更新/复制布局操作，因为匹配规则不再属于快照。保留它们会让同一行为出现两个相互冲突的数据所有者。

### 通过应用生命周期内的串行调度器执行自动捕获

注册向后兼容的新设置及默认值：`desktopRules.autoSnapshot.enabled = false`、`desktopRules.autoSnapshot.intervalMinutes = 30` 和 `desktopRules.autoSnapshot.maximumCount = 3`。状态/服务初始化后启动应用生命周期调度器；它读取有效设置，并在相关设置更改或导入后重置下次执行时间。首次捕获前等待完整间隔，一次最多运行一个捕获任务，并通过现有日志路径记录失败而不终止应用。

捕获读取一致的当前状态，写入一份 `Automatic` 快照，然后在同一次状态写入中清除超过配置上限的最旧自动快照。手动快照永远不参与清理。界面所属的计时器被否决，因为管理窗体隐藏或关闭后不应导致定时工作停止。

### 保守迁移本地文件和便携备份

首次加载时，如新状态文档不存在，则从 `window-cleanup-locks.json` 导入当前清理锁定，并将每一条 `desktop-layout-snapshots.json` 记录转换为含复制桌面规则的 `Legacy` 规则快照。当前全局桌面规则初始化为空，因为旧的具名布局未定义权威的全局规则集合。原子持久化转换结果后才视为迁移完成；旧文件保留为回滚/导入来源，不自动删除。

导出时使用包含完整状态载荷的新配置备份版本。导入通过将旧版本的布局快照转换为旧快照来兼容先前版本。先前备份既没有清理锁定也没有全局规则，因此保留当前清理锁定并以空的当前桌面规则集合开始，而不是虚构缺失值。新格式导入在替换任一应用所有文件前先暂存和验证设置及完整规则状态；成功后刷新活动界面和调度器。

### 保持恢复不触发窗口归位的语义

恢复当前手动或自动快照时，将其中保存的清理和桌面规则集合写入当前状态，不调用任何虚拟桌面或窗口 API。恢复旧快照仅替换桌面规则，并保留当前清理锁定。确认文本明确区分“恢复”和`应用桌面规则`。

立即归位被否决，因为它会将看似破坏性的配置替换与操作系统窗口操作绑定，也违背所要求的显式应用流程。

## Risks / Trade-offs

- [旧本地文件已损坏或仅有其中一个] → 独立导入每个有效来源，报告不可用历史，绝不覆盖有效的新状态文档。
- [修改的正则表达式产生宽泛匹配] → 更新时采用双向唯一性检查，应用时使用现有保守预览匹配；展示冲突而不是变更目标。
- [自动捕获与手动捕获、恢复或导入重叠] → 经共享状态服务串行化全部状态变更，并且一次只调度一个自动操作。
- [配置的间隔或保留数无效] → 在配置界面/服务中验证边界；无效值时保留上一有效调度，且绝不清理手动快照。
- [自动捕获过程中应用退出] → 使用原子写入替换并安全放弃未完成捕获；重启后不补拍。
- [早期备份缺少清理历史] → 保留当前清理规则，并将导入历史标为旧快照，而不是将不完整恢复伪装为完整恢复。

## Migration Plan

1. 新增统一状态结构、仓库、迁移读取器和状态验证，同时保持旧 JSON 文件不变。
2. 仅在新状态文档不存在时，从旧清理锁定和旧布局快照初始化状态；原子持久化转换结果。
3. 以全局管理器操作替换快照所属规则操作，再将快照管理改造成历史捕获、保留设置和仅恢复的行为。
4. 升级配置备份导出，并通过旧数据转换接受先前支持的导入版本。
5. 使用旧数据、空状态、正则更新、全部桌面同步、定时轮转、恢复不移动以及新旧备份导入手工验证升级。
6. 回滚时恢复旧应用二进制。它继续读取保持完整的原始文件；新状态文档对该旧二进制无作用。
